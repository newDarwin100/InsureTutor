讲解提示 · 练习用

第一题 · 比较表

先问“万用保险和传统保险有什么区别？”，展开引用并打开 PDF。我会说：这里的信息来自一张比较表。除了提取文字，还需要保留勾叉对应的是哪种保险，否则可能把产品特点弄反。

在同一聊天追问

再问“具体讲讲 financial flexibility”。这是一个混合语言追问，系统需要结合当前会话理解它指的是什么，然后重新查资料。

第二题 · 时间轴

问“陈先生什么时候结婚的？”。宣传册示例中，他在 30 岁结婚。这个答案需要保留时间轴上年龄和事件的对应关系，光提取出“30”和“结婚”两个词还不够。

第三题 · 正文和脚注

问“被裁员后能停缴多久？附加保障也适用吗？”。正文说明最长 365 日，脚注限定只适用于基本计划。我们给正文和脚注建立关联，命中正文后可以补回这个限制条件。

讲解提示 · 练习用

用一个追问贯穿全页

假设用户先问“定期提款有什么条件？”，然后问“那每年提款呢？”。下面就是这次追问的处理过程。

① 接收问题和会话

前端把问题和会话凭证发给 FastAPI。main.py 接收请求，language.py 识别语言，chat_history.py 读取这个会话的上下文。

② 检查输入，补全追问

先用本地规则筛查明显越界或不安全的请求，例如让它写代码、泄露密钥或提供个性化购买建议。这一步还没检索 PDF，不能判断所有问题是否被宣传册覆盖；后续检索、生成和核对还会判断范围与依据是否足够。followup.py 结合历史补全意思，把这个例子改写成“定期提款中，每年提款有什么条件？”。简单明确的情况用本地规则，其他被识别为追问的情况调用模型。如果指代不清楚，就请用户澄清。

③ 问题向量化，搜索 Top 5

index.py 用与知识库一致的 embedding 模型把问题转成向量，再到 Chroma 搜索最相近的 5 个 chunk。这里使用余弦距离，距离越小越相近。返回的是编号和距离，我们按编号取回保存的文字，不需要从向量反解原文。可展开这一步下方的 schema，说明 Chroma 记录与本地 JSON 的分工。

④ 查原文，补关联证据

answer.py 的 gather_evidence() 根据 chunk 的 evidence ID 找到原文，再补上脚注和相关条件。例如失业保障正文，需要补回“仅基本计划”的限制。当前也有针对这份宣传册的专题补充规则。

⑤ 整理模型输入

把问题、目标语言和原文一起交给模型。已经审核过的等义译文可以去重，减少上下文；有差异或风险标记的资料需要保留。历史只帮助理解问题，事实仍然来自这次检索的证据。

⑥ 生成结构化草稿

模型组织回答，并为内容选择支持它的 evidence ID。answer.py 编排这一步，responses.py 封装模型调用。这时答案还是草稿，暂时不展示给用户。

⑦ 核对答案

本地程序先检查引用是否合法，再由核对模型判断原文是否支持答案，有没有漏条件或混淆产品。比如一句话真实存在，也不能拿万用寿险的特点回答传统寿险。这些检查能减少错误，核对模型仍可能误判，因此还需要回归测试。

⑧ 展示并保存

核对通过后，后端按证据 ID 生成引用原文、文件名和 PDF 页码链接，再保存本轮会话和耗时。依据不足或检查失败时返回说明，不展示未通过的草稿。

总结并引出 RAG 知识库

历史帮助理解问题，检索找到依据，模型组织语言，核对检查答案是否被依据支持。这里的关键是：系统检索的资料从哪里来，为什么还能补回脚注？接下来讲这份 RAG 知识库是怎么准备的。

避免重复

这页讲请求怎么走；SSE 等待与延迟的取舍，留到性能页再讲。主编排是 answer.py，追问处理在 followup.py，向量化和检索在 index.py。输入规则、澄清和异常都可能提前结束请求；自动修复默认关闭。

核心代码位置

backend/app/main.py：请求入口与最终输出。services/followup.py：追问补全。rag/index.py：向量检索。services/answer.py：查原文、补证据、生成与核对的主编排。guardrails/rules.py：本地规则。services/responses.py：模型调用。services/chat_history.py：会话保存。除 main.py 外，上述路径也都位于 backend/app/ 下。

Chroma 数据在哪里

当前 Docker 把 chroma-data 卷挂载到 /app/data/chroma。项目根目录的 data/chroma 是本地开发索引，是另一份数据，不能直接当成当前 Docker 的索引。目录中既有 chroma.sqlite3，也有向量索引子目录，不能只复制一个 SQLite 文件就认为拿到了完整索引。展开关联示例可以查看当前 Docker 中的失业保障记录及其脚注，向量仅显示前 8 维。

关联图怎么讲

失业保障正文在第 11 页，p011-b003 和 p011-b004 是中英文正文。它们的 related_evidence_ids 指向 p012-b009 和 p012-b020，也就是第 12 页中英文“仅基本计划”的脚注。chunk 汇总其来源 evidence 的关联编号，因此本地 chunks.json 和 evidence.json 都能看到这些关系。Chroma metadata 没有存这个字段；检索拿到 chunk 编号后，程序查本地 JSON，再补脚注。图里的中文是摘要，准确原文在“查看记录”里。

讲解提示 · 练习用

承接在线问答

刚才讲的是用户提问后怎么处理。现在往前看一步：这些可检索、有原文出处的资料是怎么准备出来的？这条流水线在准备知识库时运行，每次提问不需要重新解析 PDF。

① MinerU 提取，统一格式

MinerU 给我们带结构的 JSON，包含页面、文字块、标题、表格和坐标。normalize_mineru.py 把它整理成统一格式，并给每个块编号。例如 p011-b002 是第 11 页第 2 个正文版面块，一个块可能是一整段，不等于一句话。

② 核对与修正

提取工具可能漏掉图中的关系，比如勾叉属于哪一列、年龄对应哪个事件。我们核对原 PDF，把修正写到 corrections.json，再由 preprocess.py 重复应用。原始提取内容保留，修正后的内容另存，所以能追溯每一处修改。

③ 建立 evidence 和 parent

evidence 是带出处的一条资料，保存文字、页码和来源位置；parent 把结构上相关的资料放在同一个组里。正文主要按标题分组，表格按行处理，编号脚注单独分组。例如“最长 365 日”的正文段落就是一条 evidence。

④ 记录关联

如果正文引用脚注，就在正文记录里保存脚注的 evidence ID。检索时顺着这个 ID，可以补回限制条件。正文和脚注可以分开存，通过 related_evidence_ids 关联。中英文的对应和差异另外保留审核记录。

⑤ 组装 chunk

chunk 是交给检索系统的文本包。同组里较短的资料可以合并，过长的资料沿句子边界拆分，当前上限是 1200 个字符。只有 100 字的组也可以保留，不用凑满。一条很长的 evidence 可能出现在多个 chunk 中，但仍能追踪回同一条证据。

⑥ 向量化，⑦ 写入 Chroma

把 chunk 的标题和文字交给 embedding 模型，得到表示内容特征的向量。Chroma 保存向量、chunk 编号、文本和元数据。清洗和切块在本地完成，到向量化这一步才调用 embedding API。

概念小结

evidence 保存原文和出处，chunk 用于检索，两者通过编号关联，所以检索结果最终能落回 PDF 原文。

技术细节备查

核心逻辑在 preprocess.py 和 index.py；prepare_knowledge.py、build_index.py 是运行入口。120 字符 overlap 用于长证据拆分，不是所有相邻 chunk 都重叠。parent 是结构分组，不保证每组只表达一个语义点。图示修正来自人工核对配置，尚未实现通用图像自动理解。

图表补全与验证 · 约 30 秒

前面演示的比较表和时间轴，在开发时实际失败过：比较表丢失产品归属，时间轴丢失年龄与事件对应。我们核对 PDF、保存修正，并把问题保留为回归案例。清洗需要检查文字，也需要检查关系是否完整。

说明验证边界

89 项是项目离线检查总数，不是单独的数据清洗测试数，也不是问答准确率。固定问题还做了简繁英实测，但已修复的案例不代表所有图示都完整覆盖。时间轴简体题还曾被范围检查拦截，调整后复测通过。

这条请求总共约 4.83 秒，生成约 2.72 秒、核对约 1.49 秒，检索约 0.60 秒。它是一条真实测量，不代表平均数或 p95。主要耗时在生成和核对。

说清优化顺序

所以我会先减少重复上下文、控制回答长度，再评估核对策略对质量和延迟的影响，而不是看到慢就直接更换向量数据库。

解释当前的流式展示

等待过程中会发送处理状态，答案通过核对后才展示。这个选择会增加等待，但避免用户先看到一段内容，之后又被撤回。当前不能承诺首字响应低于 2 秒。

先讲目录分工 · 约 1 分钟

前面讲过两条流水线，这里把它们对应到代码位置：frontend 管聊天、引用和看板；backend 管问答和 RAG 核心逻辑；scripts 提供数据准备、评测和启动入口。data 保存知识库和运行数据，evaluation 保存测试定义与结果，docs 保存 PDF、题目和开发决策。

展开 backend/app，指出四个位置

main.py 是请求入口。services/answer.py 是问答主编排，按顺序安排检索、补证据、生成和核对。rag/preprocess.py 负责整理资料、分组和切块。rag/index.py 负责向量化，以及 Chroma 的建库和搜索。

一句话记忆

main 接请求，answer 安排步骤，index 找资料。preprocess 在数据准备阶段先把资料整理好。

如果被问 scripts 和 backend 为什么分开

scripts 提供“运行某项任务”的入口，具体可复用的逻辑放在 backend。例如 prepare_knowledge.py 调用 preprocess.py，完成清洗和切块。

存储细节与边界
  • localStorage 按浏览器及访问地址隔离。localhost 和 127.0.0.1 是不同来源；清除凭证不会删除服务器上的历史，但这个浏览器会失去原列表的访问凭证。
  • 前端看板的本页汇总在内存里；每条回答已保存的耗时在 SQLite 中，重新打开聊天可以恢复对应测量。
  • 后端问题向量缓存最多 128 条、有效期 10 分钟。活动会话上下文的内存缓存可被清除；有限上下文也存入 SQLite，可以重载。
  • 未通过核对的草稿不会作为正式答案保存；问题、失败或中断状态可以保存在聊天记录中。
  • 本地开发的 data/chroma 和 data/history 与 Docker 命名卷是不同的数据位置。拉取 Git 仓库不会带走我的本地索引、聊天或真实 .env。

讲解提示 · 练习用

Docker 怎么讲 · 约 1 分钟

Docker 把应用和依赖打包成一致的运行环境。清洗后的资料已经准备好，启动时检查索引，缺失或版本变化时建立索引，有可用版本就复用。启动不会重新跑 MinerU 解析。

数据存在哪里

Chroma 索引和 SQLite 聊天历史保存在持久化卷里，重建容器可以保留数据。别人拉取代码并在自己的电脑启动后，不依赖我的电脑持续开机。

用了什么模型

当前回答和核对使用 gpt-5.6-luna，向量化使用 text-embedding-3-large，输出 3072 维向量。模型可以配置，当前实现没有完成全面的 LLM 横向对比。

避免重复

这里只讲运行环境、启动时机和持久化。向量如何生成已经在知识库页讲过，不再展开。构建索引和在线问答需要配置可用的 API key。代码入口是 start.sh、container_entrypoint.py 和 Docker 配置。

沿存储图讲：同一台电脑，四种位置

用户拉取项目后，在自己电脑构建镜像。镜像包含程序、依赖、前端页面、PDF 和已清洗资料；API key 从用户自己的 .env 在运行时注入。浏览器展示页面，后端容器处理问题，数据库通过 Docker volumes 保存在这台电脑上。

浏览器保存什么

localStorage 保存工作区和当前聊天的访问凭证，完整聊天记录在后端 SQLite 中。刷新页面后凭证还在，所以能重新读取聊天；没有发送的输入草稿和页面内存状态会重置。清空浏览器数据可能丢失访问凭证，不等于服务器上的记录已经删除。

持久化与临时数据

chroma-data 保存向量索引，chat-history 保存 SQLite 的聊天、引用和耗时。它们独立于容器，普通重建容器不丢数据。进程里的问题向量缓存、活动上下文缓存、检索结果和生成草稿是临时的；其中需要恢复的会话上下文另有 SQLite 版本。

重启与删除的区别

重启或 docker compose down 会清掉运行中的内存，保留数据卷。docker compose down -v 会连命名卷一起删除，聊天数据随之丢失，索引需要重新建立。当前这是用户自己的本地部署，不依赖开发者电脑持续开机。

最后的项目总结 · 需要时使用

我们先把 PDF 整理成带出处的 evidence，再按结构分组打包成 chunk，向量化后存入 Chroma。用户提问时，系统理解问题并检索相近 chunk，按编号查回原文、补齐脚注，然后生成并核对答案，最后展示可以点击验证的引用。
